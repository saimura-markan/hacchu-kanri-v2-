## 次回やること（3b）：見積のライフサイクル完成（設計確定）

### ステータスの流れ

```
見積依頼中 →【管理者が見積を通知】→ 見積提出済み（新規）→【顧客が施工依頼】→ 調整中（既存に合流）→ 日程確定（既存）
```

- **新しく足すステータスは「見積提出済み」の1つだけ。**
- 施工依頼の後は既存の「調整中」に乗せるので、既存の段取り・日程確定・24時間タイマーがそのまま使える。
- 段取りの提案を作る機能は新しく作らない。既存の日程確定フローを使う。

### 作るもの

1. 見積を通知したら、status を自動で「見積提出済み」に遷移させる
2. 顧客に「施工依頼」ボタン（見積提出済みのときだけ表示）
3. 施工依頼を押したら、③の詳細入力画面（鍵・駐車場・担当者・正確な住所）を再利用し、「開始希望範囲」を選んでもらう
   - 1つの日付ではなく「この範囲で開始を希望」という幅のある指定。UI は次回詰める
   - ③の詳細入力フォームを再利用できるかは次回検討する
4. 送信で status を「調整中」に昇格させ、管理者に「施工依頼が来た」ことを通知する
   - 専用のイベントを作る（Push 見出しは「E-Li 施工依頼」など。`order_received` は流用しない）
5. 以降は既存の調整中フロー（会社が段取りを提案 → 日程確定）に合流する

### 前提・あわせてやること

- **実装の前に、顧客ロールで status の UPDATE が通るかのドライランを必ずやる。** 顧客が status を進めるため。
  わざと例外で終わらせる形にし、対照は current_user・auth.uid() の一致・必ず0行になる UPDATE。
- 「見積提出済み」を足すときは、今日と同じくステータス定数・フィルタ・並び順・件数表示に漏れなく足し、既存トリガー・自動完了・タイマーへの影響を確認する。
- テストデータの物理削除（件数を数える SQL → 確認 → DELETE）
  - 対象：テストの見積依頼（KJ-240）と通常発注テスト各1件の orders と、schedules・messages・eli_order_estimates・Storage の見積PDF・eli_email_log / eli_email_sent のテスト行・cases・sites

## 注意点

- 見積依頼のテスト案件（KJ-240）は次回のテスト材料として**本番に残している**。社内に「テストなので触らないで」と周知すること。
- 見積依頼中 → 調整中 は UPDATE なので `order_received` は発火しない。今は管理者が手動で昇格しても通知は飛ばない（3b で専用イベントを作る）。
- 3b の実装後は「見積は通知済みなのに見積依頼中のまま」の案件は生まれない。それまでに入った本物の見積依頼の移行方法を次回決める。
