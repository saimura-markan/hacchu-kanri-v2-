## 次回やること（3b）：見積依頼中 → 見積提出済み → 調整中 をまとめて設計・実装

ステータスの整合性とトリガーへの影響確認を一度で済ませるため、次をセットで扱う。

1. 見積を通知したら「見積提出済み」に自動遷移
2. 顧客の「見積を承認して段取りに進む」ボタン（見積が通知済みのときだけ表示、条件付き UPDATE で二重確定を防ぐ）
3. 承認時に足りない詳細（鍵・駐車場・担当者・正確な住所）を入力するフォーム（③の統合フォーム再利用を検討）
4. 調整中への昇格＋専用通知イベント（Push 見出し「E-Li 発注確定」等。`order_received` の流用ではなく分ける）
5. その前提として、顧客ロールで status の UPDATE が通るかのドライラン（わざと例外で終わらせる形。対照は current_user・auth.uid() の一致・必ず0行になる UPDATE）
6. テストデータの物理削除（件数を数える SQL → 確認 → DELETE）
   - 対象：テストの見積依頼（KJ-240）と通常発注テスト各1件の orders と、schedules・messages・eli_order_estimates・Storage の見積PDF・eli_email_log / eli_email_sent のテスト行・cases・sites

## 注意点

- 見積依頼のテスト案件（KJ-240）は次回のテスト材料として**本番に残している**。社内に「テストなので触らないで」と周知すること。

- 3b の実装後は「見積は通知済みなのに見積依頼中のまま」の案件は生まれない。それまでに入った本物の見積依頼の移行方法を次回決める。
