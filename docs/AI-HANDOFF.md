# AI・開発者引継ぎガイド

このプロジェクトを変更・修正・追加開発する前に、必ず以下を読んでください。

コードだけで判断しないでください。

設計思想・業務フロー・権限設計・データ構造を理解してから作業してください。

---

## 必読資料

以下を順番に読み終えてから作業を開始すること。

1. `README.md` — システム全体像・起動方法・引継ぎ注意事項
2. `docs/e-li-philosophy.md` — **最優先。E-Liの存在意義と設計思想**
3. `docs/system-overview.md` — 技術スタック・外部サービス構成
4. `docs/business-flow.md` — 発注受付〜完了までの全フロー
5. `docs/screens.md` — 全画面の機能一覧・コンポーネント名・行番号
6. `docs/database-design.md` — 全テーブル定義・SQLファイル一覧
7. `docs/permissions.md` — ロール設計・RLSポリシー・通知制御
8. `CLAUDE.md` — 実装上の注意事項・変更履歴

読む順序に意味があります。思想書を読まずにコードに触れないこと。

## E-Liの重要思想

E-Liは

「便利な発注フォーム」

ではありません。

「マーカンの受発注を仕組みに変えるインフラ」

です。

開発時は以下を必ず守ってください。

- 電話・口頭・記憶への依存を増やさない
- 受付品質を担当者のスキルに依存させない
- 顧客が「いつでも・どこでも・迷わず」使える状態を維持する
- 情報はシステムが記録し、人間の記憶に頼らせない
- 将来のMK Connect連携を前提とした設計を崩さない

## 実装前報告フォーマット

実装前に必ず以下の形式で提出すること。

```
【理解した内容】

・システム概要（E-Liが何のためにあるか）
・該当業務フロー（今回の変更が関係するフロー）
・影響を受ける画面・機能

【実装内容】

・何を変更するか
・なぜ変更するか（どの思想・課題に対応するか）

【影響範囲】

・変更するファイル・行番号
・変更・追加するDBテーブル・カラム
・適用・変更が必要なRLSポリシー・SQL
・影響を受ける権限・ロール

【リスク】

・考えられる不具合・副作用
・ロールバック方法

【E-Li思想との整合性】

・受付品質の標準化: 維持する / 影響なし / 要検討
・顧客利便性の向上: 維持する / 影響なし / 要検討
・電話依存の削減: 維持する / 影響なし / 要検討
・入力ミス防止: 維持する / 影響なし / 要検討
・MK Connect連携への整合: 維持する / 影響なし / 要検討
```

## 禁止事項

以下は禁止とする。

**資料を読まずに実装すること**
- README.md・docsを読まずに実装を開始すること
- e-li-philosophy.mdを読まずにフォーム・フロー・UXに触れること

**推測による変更**
- 推測でDBテーブル・カラムを変更・削除すること
- 推測で権限・RLSポリシーを変更すること
- 根拠なく既存の業務フローを変更すること

**E-Li思想に反する実装**
- 受付品質を担当者のスキルに依存させる変更（フォームの簡略化・必須項目の削除等）
- 顧客が「今の状態」を確認できなくなる変更（ステータス非表示・履歴削除等）
- 電話依存を増やす変更（「担当者にお電話ください」という案内を増やす等）
- 入力ミス防止の仕組みを壊す変更（変更履歴・チャット自動投稿・バッジ通知の削除等）
- MK Connect連携の素地を壊す変更（case_code採番ロジック・casesテーブル構造の破壊等）

**Supabase操作**
- RLSを無効化すること（`ALTER TABLE xxx DISABLE ROW LEVEL SECURITY`）
- `anon` ロールに過剰な権限を付与すること
- サービスロールキーをフロントエンドに埋め込むこと

## 大規模変更の定義

以下は事前に承認を得てから実装すること。承認前に実装してはいけない。

**DBへの変更**
- テーブルの新規作成
- カラムの削除・型変更
- RLSポリシーの追加・変更・削除

**フローへの変更**
- 発注フォームのステップ構成の変更
- ステータス種別・遷移ルールの変更
- LiBotの自動メッセージトリガー・内容の変更
- 権限ロールの追加・変更・削除

**外部連携への変更**
- Supabase Edge Functionの変更・追加
- Storageバケット・ポリシーの変更
- Vercel設定（vercel.json）の変更
- MK Connect連携の実装開始（仕様確認後でなければ着手不可）

**設計思想への変更**
- 発注フォームの必須項目の変更・削除
- 変更履歴・ログの記録をやめること
- タイマー警告・自動完了ロジックの変更

## 開発優先順位

優先順位は以下の順番とする。

1. **E-Li思想の維持** — 標準化・利便性・ミス防止・電話依存削減に反しない
2. **データ保全** — 既存データ・履歴・ログを消さない
3. **権限・セキュリティの保全** — RLS・ロール設計を崩さない
4. **業務フローの維持** — 発注→管理→完了の流れを壊さない
5. **バグ修正** — 確認済みの不具合を修正する
6. **新機能開発** — 上記すべてを満たしたうえで追加する

新機能より既存の仕組みの保護を優先すること。

## ドキュメント更新ルール

コードを変更した場合は、対応するドキュメントも同一コミットで更新すること。

| 変更内容 | 更新が必要なファイル |
|---|---|
| 画面・コンポーネントの追加・変更 | `docs/screens.md` |
| 業務フロー・ステータスの変更 | `docs/business-flow.md` |
| テーブル・カラムの追加・変更 | `docs/database-design.md` |
| 権限・RLSの変更 | `docs/permissions.md` |
| 外部サービス・環境変数の変更 | `docs/system-overview.md` / `README.md` |
| 思想・目的の変化 | `docs/e-li-philosophy.md` |
| 実装上の注意・変更履歴 | `CLAUDE.md` |

ドキュメントを更新せずにコードだけ変更することは禁止。

コミットメッセージは以下の形式を使うこと。

```
feat: 機能追加の説明
fix: バグ修正の説明
docs: ドキュメント更新の説明
refactor: リファクタリングの説明
```

## 不明点がある場合の対応

推測で実装しないこと。

README.md・docsフォルダ・CLAUDE.mdに根拠がない場合は、実装を止めて以下の形式で報告すること。

```
【確認事項】

・確認が必要な内容
・なぜ確認が必要か
・推測した場合のリスク
・確認できれば先に進める準備はできているか
```

特に以下は必ず確認してから進めること。

- 発注フォームの項目追加・削除
- ステータス遷移ルールの変更
- SQLマイグレーションの実行（Supabase側の現状確認が先）
- MK Connect連携の実装（仕様が確定するまで着手不可）
- RLSポリシーの変更（本番への影響が大きい）

## 開発の最終目的

E-Liは、

受発注を担当者の記憶・電話・口約束に頼らせないことを目指している。

すべての開発判断は

「これはシステムを仕組みに変えるか、それとも人に依存させるか」

という問いに答えられるものでなければならない。

人に依存させる方向の変更は、たとえ短期的に便利に見えても、E-Liの存在意義を損なう。
